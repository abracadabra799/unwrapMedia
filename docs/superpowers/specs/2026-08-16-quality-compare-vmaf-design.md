# Quality Compare: VMAF Support — Design Spec

**Goal:** Add VMAF as a third, independently selectable quality metric alongside PSNR and SSIM in the existing "품질 비교" (Quality Compare) window, completing the original design spec's full PSNR/SSIM/VMAF scope. Gated behind a runtime availability check of the resolved ffmpeg binary, with an optional frame-subsampling speed-up for users who need faster (if slightly less complete) results on large files.

**Context:** This is the last remaining phase of `docs/superpowers/specs/2026-08-15-quality-comparison-psnr-ssim-vmaf-design.md` (the original full-feature spec). Phase 1 (PSNR/SSIM, single fixed pair) and Phase 3 (3-way Raw/Encoded A/Encoded B comparison mode) are both shipped — see memory `project-streameye4-benchmarking-roadmap`. This phase adds VMAF to the already-shipped `QualityCompareWindow.kt`, which today supports up to 3 comparison pairs (Raw↔A, Raw↔B, A↔B) each run through a sequential (pair × metric) queue for PSNR and SSIM. VMAF becomes a third optional item in that same queue — no new architecture, no new window.

Every ffmpeg command and log format referenced in this spec was run for real and inspected during brainstorming (not assumed): a real `libx264`-encoded MP4 pair (raw + CRF-30 re-encode) was generated via `ffmpeg -f lavfi -i testsrc=...`, then `libvmaf` was run in both `log_fmt=csv` and `log_fmt=json` to compare their shapes, and `n_subsample=5` was run separately to confirm frame numbering behavior — findings are recorded in the Technical Foundation section below.

## Scope

- **A third metric checkbox, "VMAF"**, alongside the existing PSNR/SSIM checkboxes in `QualityCompareWindow.kt`. Off by default is not required — matches the existing PSNR/SSIM checkboxes' "on by default" behavior, *if* VMAF is available; if unavailable, it starts (and stays) unchecked and disabled.
- **Availability gating:** VMAF's checkbox is disabled until a background check confirms the resolved `ffmpeg` binary actually supports the `libvmaf` filter. Verified detection method: `ffmpeg -filters` output containing the string `libvmaf` (confirmed against a real ffmpeg 8.1.2/Homebrew build during brainstorming — the filter list includes a `libvmaf` line when built with `--enable-libvmaf`). This check:
  - Runs only when the Compare window is opened for the first time in a session — never at app startup, never on the file-open path.
  - Is cached at the process level (not per-window-instance, not per-pair) — reopening the Compare window later in the same session reuses the cached result instead of re-checking.
  - Runs on the existing background executor (`qualityCompareExecutor`), never blocking window creation or the UI thread.
  - When unavailable, the VMAF checkbox is disabled and a short inline text explains why (e.g. "VMAF 사용 불가 (ffmpeg에 libvmaf 없음)") — matching this window's existing inline-status-text convention (the pair "확인 중.../일치/불일치" labels), not a new tooltip component.
- **A second checkbox, "빠른 모드" (fast mode), enabled only when VMAF is checked** — when checked, VMAF passes use `n_subsample=5` (score every 5th frame instead of every frame); unchecked (default) uses every frame. Confirmed during brainstorming: `n_subsample` genuinely reduces computed frames (verified: a 10-frame clip produced only 2 CSV rows, at real frame indices 0 and 5 — not renumbered/compacted), so the resulting `perFrame` series for a fast-mode run is sparser but still correctly frame-indexed.
- **`n_threads` is set automatically** to the machine's available processor count (`Runtime.getRuntime().availableProcessors()`) on every VMAF pass — a pure speed win with no accuracy trade-off, so it needs no UI; unlike `n_subsample`, this isn't exposed as a user choice.
- **VMAF joins the existing sequential (pair × metric) run queue** exactly like PSNR/SSIM: for each queued pair (already resolution-matched, per the existing Phase 3 gating), if VMAF is checked, a `runVmafPass` invocation is appended to that pair's queue items alongside PSNR/SSIM. No changes to queue ordering, cancellation, or progress-labeling architecture — VMAF is just a third possible metric name in the existing loop.
- **Results:** VMAF's per-pair statistics (min/max/mean/median, computed the same way as PSNR/SSIM via the existing `computeStatistics`, from the real per-frame VMAF scores — not from ffmpeg's own `pooled_metrics` block, which this feature doesn't parse) and its per-frame graph (via the existing `MetricGraph`) appear in the same grouped-by-pair-then-metric results view, ordered PSNR, SSIM, VMAF within each pair (matching each pair's fixed metric-checkbox order top-to-bottom).
- **Export:** VMAF's results flow through the existing `writeResultsCsv`/`writeMultiPairResultsJson` functions unchanged — `MetricRunResult` is metric-agnostic, so no export code changes are needed at all, only that a `"VMAF"` entry can now appear in the `Map<String, MetricRunResult>` passed to those functions.
- **CSV log format, not JSON:** VMAF passes ask `libvmaf` for `log_fmt=csv` rather than the JSON format the original 2026-08-15 spec assumed. Verified during brainstorming: `log_fmt=csv` produces a flat header row (`Frame,...,vmaf,`) followed by one comma-separated row per frame — directly parseable the same way PSNR/SSIM's stats-file lines already are, with no JSON parsing (this codebase has no JSON library, and VMAF's real JSON output is a nested structure — a `frames` array of objects each containing a `metrics` object — that would need actual JSON parsing to extract safely, unlike CSV's flat rows). This is a deliberate, verified deviation from the original spec's JSON assumption, made because it avoids introducing any JSON-parsing code (regex-across-braces or otherwise) for a codebase that has consistently avoided that complexity elsewhere.

## Technical Foundation

Verified against real ffmpeg 8.1.2 output during brainstorming (not assumed):

- **`libvmaf` filter invocation and CSV log format:** `ffmpeg -i <comparison> -i <reference> -lavfi "libvmaf=log_path=<path>:log_fmt=csv:n_threads=<N>[:n_subsample=<M>]" -f null -`. The resulting CSV's first line is a header (`Frame,integer_adm2,...,vmaf,` — the exact middle columns vary by libvmaf version/model but `Frame` is always first and `vmaf` is always present, verified as the second-to-last comma-separated field before the trailing comma on every data row). Each subsequent line is one frame's data; the `Frame` field holds the real frame index (0-based, matching this app's existing frame-indexing convention), and the `vmaf` field holds that frame's VMAF score as a plain decimal (no `"inf"` sentinel — unlike PSNR, VMAF scores are bounded and don't produce an infinity case for identical frames, confirmed: a real self-comparison in a related check produced a normal ~94-100 range score, not a special value requiring capping the way `PSNR_INFINITE_CAP_DB` does).
- **Input order:** consistent with the fixed convention already established in Phase 1 specifically because of VMAF's asymmetry (`comparison` is always ffmpeg's first `-i`, `reference` the second) — this spec's `runVmafPass` follows the exact same `(comparison: File, reference: File, ...)` parameter order as `runPsnrPass`/`runSsimPass`, requiring no new convention.
- **`n_subsample` frame-numbering:** verified — a 10-frame test clip run with `n_subsample=5` produced exactly 2 CSV rows, at `Frame` values 0 and 5 (not 0 and 1). Confirms `MetricFrameSample.frameIndex` parsed from the `Frame` column is correct and meaningful even in fast mode, with no special-casing needed in the parser.
- **`libvmaf` availability detection:** `ffmpeg -filters` output on a `--enable-libvmaf` build includes a line containing `libvmaf` (confirmed: ` .. libvmaf           VV->V       Calculate the VMAF between two video streams.`). No build-configuration-string parsing needed — a substring search on the filter list is sufficient and matches what `resolutionsMatch`/`probeResolution` already do (shell out to an ffmpeg-family binary, read its stdout).
- **CUDA acceleration:** confirmed absent from this project's development ffmpeg build (`ffmpeg -filters`/`ffmpeg -version` show no `cuda` filters or CUDA in the build configuration — this is an Apple clang/Homebrew build) and out of scope regardless, since CUDA requires NVIDIA GPU hardware this project's macOS-primary target doesn't have. Not pursued in this phase.

## Components

- **`ui/QualityMetrics.kt`** (extended) — add `fun runVmafPass(comparison: File, reference: File, onProgress: (Int, Int?) -> Unit, isCancelled: () -> Boolean, fastMode: Boolean): MetricRunResult?`, following the exact same structure as `runPsnrPass`/`runSsimPass` (temp CSV log file, `runMetricPass` with a `libvmaf=...` filter spec, parse-then-`computeStatistics`, return `null` on any failure). Add `fun isVmafAvailable(): Boolean` — a synchronous, blocking function (shells out to `ffmpeg -filters`) that the caller is responsible for invoking off the UI thread and caching; matches this codebase's convention of pure/synchronous metric-adjacent functions with no caching logic baked into `QualityMetrics.kt` itself (caching lives in the UI layer, same separation Phase 1 established between pure functions and UI-thread orchestration).
- **`ui/QualityCompareWindow.kt`** (modified) — add the VMAF and 빠른 모드 checkboxes, the availability-check-and-cache flow (triggered once per window-open, using a module-level cache so it's shared across window instances within a session), and extend the run-queue construction to append a VMAF `QueueItem` when checked.
- No new files. No changes to `QualityExport.kt`, `MetricGraph.kt`, `Main.kt`, or the `determineComparisonPairs` pair-determination logic (all metric-agnostic already).

## Error Handling

Matches this codebase's established convention, already used by `runPsnrPass`/`runSsimPass`:
- `runVmafPass` returns `null` on any failure (process error, non-zero exit, cancellation, unparseable CSV) — the caller (the run queue) already handles a `null` metric result by simply omitting that metric from the pair's collected results, exactly as it does today for a failed PSNR/SSIM pass. No new error-handling code needed in `QualityCompareWindow.kt` beyond adding VMAF to the existing `when (item.metricName)` dispatch.
- `isVmafAvailable()` never throws — a failure to invoke `ffmpeg -filters` (e.g. `FfmpegLocator` misconfiguration) is treated the same as "libvmaf not found": the checkbox stays disabled.

## Testing

Follows this codebase's established real-fixture convention (matching `QualityMetricsTest.kt`'s existing `runPsnrPass`/`runSsimPass` tests):
- `runVmafPass` tested against real generated clips (same `generateTestClip`/`reencode` helpers already in `QualityMetricsTest.kt`): a normal two-different-encodes case (finite, in-range score), a `fastMode = true` case (confirms fewer frames are returned, at correct non-sequential frame indices), a cancellation case (returns `null`), and a progress-reporting case.
- `isVmafAvailable()` is tested against the real system ffmpeg (expected `true` in this project's dev/CI environment, which already has `libvmaf` — confirmed during brainstorming) — matching how `resolutionsMatch`'s tests already invoke real `ffprobe`.
- No automated test for the `QualityCompareWindow.kt` UI wiring (checkbox enable/disable, caching), matching this codebase's established convention for Compose UI tasks — manual verification only.

## Out of Scope (Deferred)

- CUDA/GPU-accelerated VMAF (`vmaf_cuda`) — no target-platform hardware benefits from it; revisit only if a future ffmpeg bundle adds CUDA support on a platform where it matters.
- VMAF model selection (custom/4K models) — uses ffmpeg's default model only, matching the original spec's Phase 1 decision for this same deferral.
- User-configurable `n_threads` — always automatic (CPU core count), never exposed as a UI choice.
- A numeric/custom `n_subsample` value — 빠른 모드 is a fixed binary choice (off = every frame, on = every 5th frame), not a tunable interval.
